# Исправление подбора комплектных систем

Проверено 21 октября 2026 года. Исправление относится к Manager и импорту API;
категория полупрома и форма блока сами по себе не подтверждают комплектность.
Правила выполнения операций находятся в
[production data operations](production-data-operations.md).

## Поведение и проверка

- Обычный порядок `recommended`: настенные первыми, затем название и ID;
  сортировка выполняется до пагинации, другие формы остаются в количестве и выдаче.
- Явная форма обязательна. Явная сортировка по колонке имеет приоритет над
  обычным порядком; интерфейс позволяет вернуться к нему и сохраняет выбор в URL.
- Номинал берётся из `specs.capacity_cooling_kw`, основное поле согласуется с ним
  при импорте, создании, дублировании и обычном сохранении карточки.
  Для чтения и записи допустим только положительный конечный номинал;
  недопустимая характеристика не перекрывает допустимое основное поле.
  Потребление и пределы модуляции не заменяют номинал.
- `7 кВт` означает ровно 7 кВт номинальной холодопроизводительности.
  Явные `100 кВт` и `125 kw` сохраняют масштаб числа; эвристика ватт,
  используемая для некоторых источников импорта, не применяется к поиску.
  Классы БТЕ объединяются через ИЛИ, разные условия — через И.
- Температура и наличие остаются обязательными; включение заказных снимает
  только ограничение наличия. Неподтверждённая температура не считается совпадением.
- Новые импорты сохраняют классификацию по явным характеристикам. Повторный
  импорт сохраняет существующий осознанный вид товара; исторические `other`
  требуют адресной проверки. При полном сохранении `unknown` разрешается по
  характеристикам так же, как при создании. Новый полупром с неподтверждённым
  составом остаётся `unknown`, чтобы дальнейший импорт с явным подтверждением
  комплекта мог уточнить вид; известный комплект из нескольких внутренних
  блоков сохраняет исключение из подбора.
- Список, сравнение, корзина и перенос в предложение используют общий строгий
  допуск комплектных систем и существующие ограничения компаний.
  Явное отрицание наличия любого блока исключает товар независимо от
  сохранённого ручного вида. Проверяются обычные и типизированные значения,
  включая `false`, `0` и `нет`. Отсутствие сведений само по себе не отменяет
  ранее установленный вид; ручной вид при этом не перезаписывается.

Регрессионные проверки находятся в
`tests/integration/test_catalog_decision_query_postgres.py`,
`tests/integration/test_catalog_decision_regressions_postgres.py`,
`tests/integration/test_catalog_equipment_import_persistence.py`,
`tests/integration/test_catalog_decision_data_repair_postgres.py` и компонентных
тестах Manager. Перед параллельными PostgreSQL-проверками выполнено доказательство
физической изоляции четырёх баз по [процедуре тестов](development-workflow.md#backend-tests).

## Свежие наблюдения

Публичные три страницы полупрома и read-only снимок основной БД содержат
258 товаров: 22 `complete_split_system`, 223 `other`, 13 `unknown`.
В БД 19 KINGHOME имеют оба явных признака блока и один внутренний блок;
у №1307 флаги сохранены строками `"true"`. Ни один не относится к `cat-multi`.

Прямой вызов рабочего серверного подбора в системной компании 1, витрине 1
в read-only транзакции проверил 72 варианта: напольно-потолочный, канальный,
кассетный; классы 36, 42, 60 отдельно и вместе; без температуры, −20, −25;
только наличие и включая заказные. Все варианты пустые. Это проверка рабочей
проекции; она не подменяет проверку HTTP с авторизацией и выбранной компанией
после выпуска и исправления данных.

Для KINGHOME №94, №97, №98 первичная причина — сохранённый вид товара;
их номинал и температура соответствуют 60/36/42 и −25 соответственно.
У TCL №180 независимая причина — `power_cooling=5.69` при номинале 16.12;
его подтверждённый обогрев только до −7, поэтому −20/−25 по-прежнему исключают
его после исправления мощности.

## Выполнение и повторная проверка

Выполнять из точного выпущенного образа на проверенном основном узле под
существующим deployment lock. Сначала сохранить полный свежий JSON плана:

```bash
python3 scripts/repair_catalog_decision_data.py
```

После проверки всех 34 операций и ручного согласования использовать этот же
JSON, его `plan_digest` и отдельное подтверждение проверки старых видов:

```bash
python3 scripts/repair_catalog_decision_data.py \
  --execute \
  --reviewed-plan /tmp/reviewed-catalog-decision-plan.json \
  --execute-plan-digest REVIEWED_SHA256 \
  --confirm-manual-kind-review-digest REVIEWED_SHA256
```

`REVIEWED_SHA256` — значение из конкретного отчёта, не произвольный токен.
План действует 30 минут; исполнение повторно проверяет тот же manifest и
наблюдаемое состояние, блокирует строки и требует `pg_is_in_recovery()=false`.
Изменения, ревизия каталога и событие очистки кешей фиксируются атомарно.
При ошибке транзакция откатывается. Для повторного запуска строится свежий план;
после достижения точного результата он содержит ноль изменений и не пишет
новую ревизию. Частично изменившееся или неизвестное состояние блокируется.

После операции повторить те же 72 запроса и явно проверить KINGHOME №97/98/94,
TCL №180 без температурного ограничения, общий порядок и количество до/после
пагинации, сохранение фильтров и доступ текущей компании через Manager HTTP.
Успешный выпуск кода без возврата подтверждённых комплектов в рабочую выдачу
не означает закрытие проблемы. Обязательные smoke checks описаны в
[deployment verification](deployment.md#verification).

## Отдельные расширения

Класс 48 отсутствует в общем `BTU_MAPPING`, из-за чего номиналы между 13 и 15 кВт
не попадают в существующие классы. Граница 11 кВт входит и в 36, и в 42.
Менять общие диапазоны в этом исправлении нельзя без оценки публичного smart
search и отдельного согласованного правила границ. Точный поиск в кВт позволяет
найти такую мощность без неявного расширения.

После 19 подтверждённых KINGHOME остальные 217 исключённых товаров не получают
автоматическую комплектность. Продолжение адресной проверки источников и ручных решений ведётся в
[задаче №1190](https://github.com/mvnby/air-api/issues/1190), включая 12 конкретных
кандидатов TCL с точными страницами первичного каталога.

Разбор по источникам дал следующие группы:

| Группа | Количество | Причина и состояние доказательств |
| --- | ---: | --- |
| MDV | 87 | Нет явного канонического состава; ссылки производителя и принятый экспорт требуют адресного сопоставления комплектов и ручных решений. |
| Energolux | 77 | Нет явных флагов. Все ID найдены в свежем прайсе Severcon; у №504 различаются модели в названии и параметре, ещё у четырёх различается написание C/С. |
| Hisense | 30 | Есть таблицы пар HEAVY EU/Classic у производителя, но нет подтверждённого канонического состава и истории ручного вида. |
| TCL | 16 | У 12 есть таблицы внутренних/наружных блоков в PDF; ещё четыре опираются на поставщика или содержат конфликт. Изменение мощности не меняет их вид. |
| Hisense, отдельные блоки | 3 | Мультисплит-компоненты; исключение сохраняется. |
| Chigo | 4 | Недостаточно данных о составе, точный первичный источник комплекта не подтверждён. |

Итого: 210 неподтверждённых, три отдельных блока и четыре с недостаточными
данными. Среди отдельных блоков Hisense
№1080/1082/1084, что подтверждает
[страница производителя](https://hisense-air.ru/product/multi-eu-dc-inverter-canal/).
Состав пар и карточек других источников требует адресной проверки, включая
ручные решения. Массовый `backfill_product_kinds.py --repair-conflicts` и общая
нормализация не входят в этот план.
