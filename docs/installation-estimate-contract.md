# Единая смета монтажа: целевой контракт (#955)

Статус: **целевой контракт и этапный план**. Основа — [issue #955](https://github.com/mvnby/air-api/issues/955). Денежная граница смета → заказ → документ проверена отдельными PR; новый checkout подключается только после отдельного confirm/attach пакета и проверки витрины.

## Что есть и что меняется

До первого backend-пакета `ServiceTariff`/`ServiceTariffRule` и `ServiceEstimate` обслуживали Manager и публичный расчёт услуг по выбранному `tariff_id`; основной сайт и checkout использовали отдельный `InstallationRate`/`InstallationPricingService`. Первый backend-пакет добавляет типизированные draft-поля к тому же `ServiceTariff`, публикацию неизменяемых версий книги, `resolve` и `preview`. Старые endpoints и checkout пока сохраняют свои read paths. Прямого переноса сметы в предложение с immutable revision ещё нет.

В первом backend-пакете Manager публикует `POST /api/manager/tariffs/price-book/publish` после заполнения `installation_code`, `installation_match`, `installation_price_mode`, включённых объёмов и `component_code` для активных правил. Отчёт `GET /api/manager/tariffs/price-book/legacy-comparison` даёт только кандидатов и различия цен, без копирования и утверждения. Публичные `POST /api/v1/service-pricing/installation/resolve` и `/preview` используют только опубликованную книгу своего tenant и отвечают `private, no-store`. Партнёрский scope выбирается подписанным storefront-контекстом; для канонической витрины сохраняется существующая совместимость с неподписанным контекстом, когда `STOREFRONT_CONTEXT_REQUIRE_SIGNED_REQUESTS=False`. Preview требует `Idempotency-Key` и сохраняет scope-bound снимок с хешем непрозрачного токена на 30 минут. Повтор того же ключа и входа возвращает прежний результат; повтор ключа с другим входом даёт `409`. Просроченные снимки удаляются ограниченными порциями. `quote` не выдаёт итог, `from` явно помечает нижнюю границу.

Следующий backend-пакет подтверждает `fixed` preview **только в Manager**: членство сотрудника задаёт tenant/storefront, а заблокированный заказ и целевое предложение проверяются сервером. `product_id` даёт скидку комплекта только при наличии оплачиваемой товарной строки нужного количества именно в этом предложении; для ручного service-only профиля менеджер явно подтверждает проверенные ключи установки, и actor сохраняется в неизменяемой ревизии. Подтверждённая ревизия живёт отдельно от 30-минутного preview и читается после его очистки. Привязка добавляет строки только к указанному черновому предложению: по умолчанию одну фактологическую строку, по выбору подробные строки с теми же копейками. Ключ установки — её идентификатор в предложении: повтор того же ключа не создаёт вторую работу даже с новым preview/ref; новый ключ означает явно отдельную установку. Товарные установки дополнительно ограничены суммарным количеством продаваемого оборудования по всем уже привязанным ревизиям. Повтор команды не добавляет второй счёт; выпущенные документы не переписываются.

Публичный `confirm`, подключение корзины/checkout и автоматическая привязка к заказу остаются отдельным пакетом. Сейчас публичный `preview` не доказывает владение существующим заказом: принимать клиентский `order_id`, `product_id` или `confirmed=true` как такое доказательство нельзя. Для публичного подтверждения сначала нужен проверенный контракт авторизации покупателя/заказа и состава предложения.

Цель: **один редактируемый tenant-scoped каталог `ServiceTariff`/rules на компанию**, который одинаково читает её Manager и её витрина. У основного бизнеса и каждого партнёра свои цены, доступность услуг и опубликованные версии `price_book`; шаблон при onboarding — начальная копия, последующие обновления владельца шаблона не меняют цены партнёра. `InstallationRate` остаётся временным совместимым read path, но двусторонней синхронизации, второго редактируемого прайса и переноса цен без сверки нет. Публикация новой книги атомарно валидирует покрытие и конфликты; опубликованная ревизия неизменяема, draft редактируется отдельно.

## Профиль, разрешение и состав

Resolver строит профиль из нормализованных характеристик продаваемой конфигурации: `product_kind`, `specs.type`/`specs.indoor_type` (wall, cassette, duct, floor_ceiling, column и другие явные типы), `capacity_cooling_kw`, `pipe_liquid` + `pipe_gas`. `Product.power_cooling` — только проверенный compatibility-вход; `area_m2` не выбирает тариф. Вес в кг (`weight_indoor`/`weight_outdoor`, а упакованный — только для явного правила перевозки) требуется лишь matcher-ом, которому он нужен. Если без веса нельзя проверить более специфичный подходящий тариф, результат — `quote`; правило другого типа, мощности или труб не блокирует подходящий тариф. Для ручного сценария без товара нужен такой же типизированный и подтверждённый профиль, а не имя товара. Не угадывать тип по заголовку при каждом расчёте.

Сначала проверяются комплектность/допустимость и тип оборудования, затем пара труб и числовые диапазоны мощности/нужного веса. Разные cassette и floor_ceiling не объединяются. Самое специфичное правило побеждает; два равноспецифичных совпадения — `conflict`, блокирующий публикацию, а не выбор по ID. Нет подходящего тарифа либо обязательных для него данных — `quote` с кодом причины и без фиктивной суммы; отдельный блок/аксессуар или выключенное направление — `unavailable`. Запрещены `unknown → wall`, подбор по площади и подмена отсутствующей цены последним настенным тарифом.

Режимы опубликованного тарифа: `fixed` — точная цена подтверждённого состава; `from` — нижняя граница с необходимостью уточнения; `quote` — ручной расчёт. `from` и `quote` не превращаются в фиксированную доплату в cart/checkout. Сервер возвращает объяснение выбора, включённые/исключённые работы и клиентский текст из структуры тарифа.

Каждая установка передаёт фактические `route_length_m` и `holes_by_type` явно, включая пустой объект при отсутствии отверстий. Книга хранит включённые объёмы по тем же единицам; оплачиваемое превышение каждого компонента равно `max(0, actual − included)` и использует опубликованное правило. Preview возвращает по каждой установке структурированные `actual`, `included`, `extra` и клиентский текст из этих данных; произвольное описание draft-тарифа не служит подтверждением выполненного состава. Цена дополнительной трассы зависит прежде всего от пары труб. Например, включено 3 м, фактически 6 м: три дополнительных метра, но в описании «трасса 6 м». Одно включённое и два фактических алмазных отверстия: одно дополнительное; другие типы отверстий не смешиваются с алмазными. Штробление — отдельный компонент.

Строки и опции имеют стабильные коды, единицу, количество, цену и человекочитаемое описание: например, `installation.base`, `route.extra_m`, `hole.diamond.extra`, `pump.supply`, `pump.install`, `access.scaffold`, `access.lift`. Новые коды добавляются в каталог, но смысл опубликованного кода не меняется задним числом. Все extras по умолчанию выключены. Поставка насоса и монтаж насоса — разные компоненты; насос заказчика даёт только монтаж, отдельно проданный насос не начисляется второй раз. Леса и вышка выбираются явно; общая вышка/выезд на объект учитывается один раз, а трасса и отверстия принадлежат отдельным установкам. Два этапа выполнения/оплаты распределяют **уже рассчитанный** состав, не создают вторую стоимость полной установки; правила документа о двух этапах остаются в [отдельном контракте](b2c-two-stage-installation.md).

Расчёт: базовые установки + превышения включённого + явно выбранные extras по установке + общие затраты объекта − именованные допустимые скидки. Скидка комплекта «оборудование + монтаж» требует отдельного именованного правила, чтобы её не потерять и не применить дважды. Денежная точность, округление строки, распределение скидки и допустимые единицы количества наследуются из **проверенного денежного PR**; ни web, ни адаптер заказа не пересчитывают сумму самостоятельно.

## Ревизия, предложение и документы

Каждый подтверждённый расчёт сохраняет неизменяемую `estimate_revision`/snapshot: `tenant_id`, `storefront_id`, `price_book_id` и revision, версию resolver-а, профиль и источник каждого признака, фактическое/включённое/превышение, выбранные коды, цены/скидки/итог, клиентский текст, момент расчёта и actor. Существующая ревизия не перезаписывается, даже если тариф архивирован или удалён. Исторические сметы/заказы читаются из своих снимков. В этом пакете нет команды замены уже привязанного монтажа: для пересмотра создают **новое пустое черновое предложение**, получают новый preview и подтверждают его там. Копия предложения сохраняет ссылки на исторические ревизии, поэтому не служит заменой пустому варианту. Будущая команда явной ревизии/замены потребует отдельного контракта с происхождением и причиной.

Серверная команда «добавить смету в предложение» проверяет tenant, storefront, заказ, целевой `proposal_id`, статус и конкретную `estimate_revision`, затем атомарно сохраняет ссылку и строки в выбранном предложении. Цена и текст из браузера не являются полномочием. По умолчанию клиент получает **одну грамотно составленную строку** на согласованную группу монтажных работ с фактическими объёмами и выбранными extras; режим `detailed` — только проекция той же ревизии. `Σ detailed net lines = collapsed line = estimate total = сумма монтажа в выбранном предложении/новом документе`, включая копейки и скидку. У альтернативного предложения свой состав. Issued документы не меняются: пересмотр ведёт к новому пустому предложению, а не к переписыванию выпущенного документа. Ручной override текста и замена ревизии требуют отдельной команды и в этом пакете недоступны.

## Минимальные операции API (будущий дизайн)

`resolve` и публичный `preview` реализованы в первом backend-пакете; подтверждение и привязка ниже пока доступны только в Manager. Публичный `confirm` остаётся будущей операцией. Схемы и operation IDs опубликованных операций закреплены в OpenAPI. `Money` означает точную денежную величину и сериализацию из денежного PR, `Quantity` — проверенную единицу/точность; `null` у цены для `quote` не означает бесплатную услугу.

| Операция | Вход | Выход и поведение |
| --- | --- | --- |
| `resolve` | Ровно один из `product_id` и разрешённого `typed_profile` без товара | `status: fixed \| from \| quote \| unavailable`, `reason_code`, профиль и `matched_by`, `tariff_code`, серверный `scope_ref`, опубликованные `price_book_id/revision`, `included`, `available_extras`, `explanation`; конфликт публикации не выдаёт случайный тариф. |
| `preview` | Обязательный `Idempotency-Key`; `installations[] {key, product_id \| typed_profile, route_length_m: Quantity, holes_by_type, extras[] {code, quantity}}`, `site_extras[] {code, quantity}`, необязательная ожидаемая revision | `status`, `scope_ref`, `currency`, `components[] {code, installation_key \| site, unit, quantity, unit_price, gross, discount, net}`, `installations[]` с фактическим/включённым/превышением и выбранными extras, общие `site_work`, subtotal/discount/total по денежному контракту, `customer_text`, `price_book_revision`, `preview_ref` и срок действия. Для `from` total — лишь помеченный минимум, для `quote` точного total нет. |
| `confirm` (Manager) | `preview_ref`, `order_id`, `proposal_id`, проверенные service-only keys и `Idempotency-Key`; цена не принимается | Сервер повторно проверяет membership/scope, опубликованную книгу и состав целевого предложения; только `fixed` атомарно создаёт принятую `estimate_revision`. Изменение книги/состава возвращает `409 price_changed` со свежим preview и требует нового согласия; просроченный/чужой ref не принимается. |
| `attach_estimate_to_proposal` (Manager) | `estimate_id`, точная `revision`, `order_id`, `proposal_id`, `collapsed \| detailed`, `Idempotency-Key` | Scoped ссылка на сохранённую ревизию и одна из двух равносуммовых проекций; отсутствие прав или чужой scope — нейтральный отказ. |

Публичный scope определяется доверенным host/подписанным gateway по [контракту витрины](storefront-context-contract.md), с сохранением текущей канонической совместимости при выключенном `STOREFRONT_CONTEXT_REQUIRE_SIGNED_REQUESTS`; Manager — текущим membership/storefront. Клиентский `tenant_id`, `storefront_id`, `tariff_id` или цена не служат подтверждением прав. Preview требует `Idempotency-Key` для обоих вариантов контекста. Защищённые preview/ref — `private, no-store`; shared price cache до отдельного решения не нужен. `preview_ref` непрозрачен, привязан к scope, входам и опубликованной ревизии. Идемпотентный повтор `confirm` возвращает тот же результат без повторного начисления. Legacy `installation_rate_id` и старые входы принимаются только совместимым адаптером с явным отображением в новую книгу либо сохраняют прежний read path до переключения читателя; они не создают новый тариф и не обходят server validation.

## Последовательность и критерии перехода

1. **Зависимость P0:** завершить денежный PR и проверить expand/rollout обеих API-нод, равенство одной/подробных строк, копейки, скидку и документы. До этого нельзя выдавать новый `fixed` checkout как точный.
2. **Backend-пакет после согласования этого контракта:** добавить tenant-owned draft/published price book и стабильные коды без изменения production-цен; типизированные matcher/профиль, проверку конфликтов/покрытия, server `resolve` и `preview`, неизменяемый ref/snapshot, shadow-сравнение с legacy. Схемы/OpenAPI/generated client и unit/PG integration tests обязательны. Прямое переключение checkout, запись новых денег в старую схему и удаление `InstallationRate` в этот PR не входят. Начать с read-only отчёта соответствия старых ID/цен по компаниям; расхождения утверждает владелец прайса.
3. Отдельным backend PR подключить Manager `confirm` и scoped `attach_estimate_to_proposal`, проверить идемпотентность, альтернативные предложения и неизменность выпущенных документов. Следующим пакетом определить публичное подтверждение с полномочием на заказ/состав и убрать повторное чтение изменяемой цены в website-order адаптере. Manager получает default collapsed и явный detailed switch только после этого.
4. Перевести web последовательно: партнёрский preview → основной калькулятор → карточка → корзина → checkout. Клиент показывает серверные `fixed/from/quote/unavailable`, передаёт ref, но не содержит независимой формулы. Защитить main тему/SVG и партнёрские CSP/protected 401; rollout и проверка каждой витрины отдельно.
5. До отключения legacy сравнить старый и новый путь на опубликованных версиях, объяснить различия, зафиксировать покрытие и наблюдать оставшихся потребителей. Затем сделать legacy API совместимым чтением из канонического каталога и закрыть независимое редактирование. Старый read path оставить для отката без отката данных; удалить код/таблицы только отдельным PR после нулевого использования. Старые snapshots и issued docs продолжают читаться.

Приёмка backend и web по #955: настенный/кассетный/канальный/напольно-потолочный комплект, отдельный блок, неизвестный/неполный профиль, границы мощности и условный вес не дают wall fallback; две равноспецифичные записи блокируют публикацию. Проверить 3→6 м трассы по правильной паре труб, 1→2 алмазных отверстия, дробный допустимый объём, extras off, насос поставка/монтаж, одну общую вышку для двух установок и два этапа без двойной оплаты. Для двух компаний цены и ref не пересекаются, выключенное направление не раскрывает тариф, изменение опубликованной цены даёт `price_changed`. Старая ревизия и issued документ не меняются после правки тарифа; collapsed/detailed/выбранное предложение/новый документ дают один итог по денежному контракту. Каждый этап переключения требует соответствующих API и браузерных регрессий, а не календарной даты.
