# Исправление фильтра формы внутреннего блока

## Проверенный срез

22 сентября 2026 года выполнен запрос только на чтение к 1 241 товарам в
производственной БД. На момент проверки PostgreSQL на `zakup` был primary,
а на `mvn-api` — replica. Роли нужно проверить заново перед исполнением.

| Видимый `indoor_type` | Товаров | Неверный/отсутствующий служебный тип |
| --- | ---: | ---: |
| Настенный | 711 | 711 |
| Консольный | 10 | 4 |
| Кассетный | 78 | 0 |
| Канальный | 106 | 0 |
| Напольно-потолочный | 69 | 0 |
| Колонный | 22 | 0 |

У 709 настенных товаров отсутствует `__filter_indoor_type`; ещё у двух он
равен `wall`. У всех 711 типизированное значение равно `настенный`, а не
`wall`. У четырёх консольных товаров (ID 1087–1090) фильтр отсутствует,
а типизированное значение равно `консольный`. Это объясняет отсутствие
моделей 30/36 при выборе «Настенный» и [нулевую выдачу для четырёх Hisense
AKT](https://api.mvn.by/api/v1/products?q=AKT&indoor_types=console&limit=100).

В текущем срезе ошибок в типизированном Wi-Fi и минимуме температуры
обогрева не обнаружено. Для 90 записей с диапазоном охлаждения через тире
публичное значение и типизированный минимум согласованы; исправление
разбора тире предотвращает ошибки при повторной нормализации и новых импортах.
Отдельная проверка ключей нашла 177 не зарегистрированных названий, в том
числе служебные поля источников. Например, 88 карточек содержат исходное
«Управление c мобильного приложения по Wi-Fi», но все 88 уже согласованы с
каноническим `wifi_ready`. Массово переименовывать неизвестные ключи без
проверки их смысла не требуется для этого фильтра.

Дополнительная проверка показала, что у 32 MDV сохранено `wifi_ready=false`,
хотя теги указывают на возможность Wi-Fi. Для восьми моделей INTEGRA Pro и
INTEGRA Pro Black [официальный каталог INTEGRA Pro](https://mdv-aircond.ru/catalog/bytovye-split-sistemy/invertornye-split-sistemy/integra-pro/)
и [INTEGRA Pro Black](https://mdv-aircond.ru/catalog/bytovye-split-sistemy/invertornye-split-sistemy/integra-pro-black/)
подтверждает встроенный модуль. Для двух моделей INFINI On/Off R32
[официальная карточка серии](https://mdv-aircond.ru/catalog/bytovye-split-sistemy/on-off-split-sistemy/infini-r32-on-off/)
указывает опциональное управление по Wi-Fi. Остальные 22 записи не меняем:
описания серий и комплектации расходятся, нужен первоисточник для конкретной
партии или поставщика.

## Граница исправления данных

Скрипт `scripts/repair_catalog_indoor_type.py` берёт форму только из явно
записанного `specs.indoor_type` и меняет лишь
`specs.__filter_indoor_type` и `specs.__typed_specs.indoor_type`. Остальные
характеристики, теги, категории и цены сохраняются. Товары без явной формы
блока не классифицируются по названию. Изменения вызывают обновление ревизии
каталога и событие очистки кеша в той же транзакции.

## Порядок выполнения

Следовать [правилам операций с производственными данными](production-data-operations.md)
и [правилам текущей топологии](postgres-quorum-runbook.md). Сначала выпускать
проверенный код через `main` и успешный deploy. Выполнять скрипт только из
текущего immutable API-контейнера на подтверждённом PostgreSQL primary.

1. На обоих узлах проверить `pg_is_in_recovery()` и digest активного API-образа.
2. Запустить `python3 scripts/repair_catalog_indoor_type.py` без параметров.
   Это read-only план с точным `plan_digest`, количеством изменений по формам
   и причинами расхождений. Ожидаемая исходная величина — около 715 товаров;
   любое изменение среза требует отдельной проверки плана.
3. Сверить план с видимыми характеристиками и выполнить только
   `python3 scripts/repair_catalog_indoor_type.py --execute-plan-digest <plan_digest>`
   на том же primary. Несовпадение digest или запуск на replica блокирует запись.
4. Повторить план: `changed` должен стать `0`. Проверить публичные запросы
   [Hisense AKT](https://api.mvn.by/api/v1/products?q=AKT&indoor_types=console&limit=100)
   и выдачу Manager для настенных 30/36, затем штатные `/api/health`,
   `/api/v1/products?limit=5` и `/api/v1/filters/config`.

Не запускать общий `normalize_legacy.py` ради этой задачи: он меняет видимые
поля и может переклассифицировать товары без подтверждённого первоисточника.

## Подтверждённые исправления Wi-Fi

`scripts/repair_catalog_wifi.py` меняет только поля Wi-Fi у десяти
перечисленных в `services/catalog_wifi_repair.py` товаров. Перед применением
проверяются точные ID и названия моделей, прежнее значение источника и digest
плана; остальные характеристики остаются без изменений. На текущем primary,
после выпуска кода и повторной проверки топологии:

1. Запустить `python3 scripts/repair_catalog_wifi.py` и сверить список из
   восьми `builtin` и двух `ready` с источниками выше.
2. Выполнить только `python3 scripts/repair_catalog_wifi.py --execute-plan-digest <plan_digest>`.
3. Повторить план и убедиться, что `changed=0`, а публичные карточки содержат
   исправленные типизированные значения и фильтры.

## Отсутствующие теги Wi-Fi у TCL

После исправления характеристик проверка связей с тегами выявила шесть TCL:
ID 88–91 имеют `wifi_state=builtin`, ID 159 и 715 — `wifi_state=ready`,
но ни у одного не был привязан соответствующий тег `wifi-builtin` или
`wifi-ready`. Скрипт `scripts/repair_catalog_wifi_tags.py` только добавляет
подтверждённый уже сохранённой характеристикой тег. Он проверяет точные
названия моделей, текущее состояние Wi-Fi, отсутствие конфликтующего тега,
наличие обоих канонических тегов и digest плана.

На подтверждённом primary после выпуска кода запустить read-only
`python3 scripts/repair_catalog_wifi_tags.py`, сверить шесть ID и тегов,
затем под блокировкой deploy выполнить только
`python3 scripts/repair_catalog_wifi_tags.py --execute-plan-digest <plan_digest>`.
Повторный план должен показать `changed=0`; проверить фильтрацию по тегу
`wifi-builtin` и наличие связей у всех шести товаров.
