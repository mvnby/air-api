# Граница будущей интеграции поставщика

Проверено по коду 7 октября 2026 года. Внешний supplier API и учётные данные
поставщика сейчас отсутствуют. Этот документ определяет вопросы до прототипа;
он не обещает новые endpoints, scopes или готовый формат обмена.

## Что уже реализовано внутри платформы

| Возможность | Реализованный контракт |
| --- | --- |
| Профиль поставщика, контакты и склады | Внутренние `/api/manager/suppliers/*`; [маршруты](../../routers/manager_supply.py), [сервис профилей](../../services/supply_request_service.py) |
| Источник прайса и анализ колонок | `/api/manager/supplier-sources/*`; конфигурация источника, Google spreadsheet/tab и адаптеры синхронизации — [catalog service](../../services/supplier_mapping_service.py), [sync service](../../services/supplier_sync_service.py) |
| Предложения и привязки к каталогу | `/api/manager/supplier-offers/*`, `/api/manager/supplier-mappings/*`, предложения товара; [сервис привязок](../../services/supplier_offer_mapping_service.py) |
| Внутренние заявки на поставку | `/api/manager/supply-requests/*`; сборка из строк заказа или пополнение склада, статусы и текст сообщения — [сервис поставок](../../services/supply_request_service.py) |

Все эти операции входят в платформенную группу
[Manager permission policy](../../routers/manager_permission_policy.py) и требуют
Manager-доступа системного tenant. Профили, источники, предложения и заявки
поставок общие для платформы: `supplier_id` — идентификатор записи, а не
доказательство права вызывающего клиента. Проверка заказа при сборке заявки
из его строк дополнительно использует scope текущего Manager.

Manager JWT/cookie, сервисный `BOT_API_TOKEN` и личный OAuth grant коннектора
имеют другие владельцы и назначение. Их нельзя считать supplier credentials.
Нынешний доступ не ограничивает внешнего поставщика только его предложениями.

## Ограничения текущего обмена

- Синхронизация читает настроенные источники платформенными интеграциями;
  поставщик не отправляет изменения через свой HTTP API. У Google-источника
  есть разбор колонок, внешнего ID, количества, валюты и source URL; другие
  адаптеры могут иметь свои правила. Сохранение источника не запускает sync.
- Результат sync содержит `status` и `error`: HTTP 200 не гарантирует успешный
  импорт. Повтор запускает новый sync. Деактивация отсутствующих предложений
  зависит от адаптера и конфигурации; для Google-источника она выполняется
  при не более чем одном активном источнике данного поставщика.
- Привязка использует ключ поставщик/внешний ID. Старый `POST` сообщает
  конфликт как `400`; `PUT` по offer ID проверяет ожидаемую привязку и даёт
  `409` при конфликте. Bulk создаёт записи поштучно и не обещает атомарности.
- Генерация текста сообщения поставщику/логистике не доставляет сообщение.
  `mark_sent` меняет снимок, время и состояние заявки/строк; это не
  подтверждение получения внешней системой.
- Публикация товара и цены витрине регулируется
  [shared catalog/grants](../shared-catalog-grant.md#data-and-visibility-contract).
  Эти grants не являются supplier entitlement и не дают доступ к чужим ценам,
  остаткам, клиентам или заказам.

## Решения до прототипа

| Решение | Что нужно зафиксировать |
| --- | --- |
| Сценарий и направление | Чтение каталога, push прайса/остатков, pull платформой, подтверждение заявки или обмен документами? Начать с одного сценария и его потребителя. |
| Идентичность и доступ | Как организация связывается с supplier record, кто подтверждает связь, как выдаётся и отзывается credential, какие операции и данные ему доступны? Не наследовать системные Manager-права. |
| Владелец и область данных | Кто владеет SKU, названием, ценой, валютой, остатком, warehouse, source и mapping; кто исправляет ошибки и разрешает конфликты? Какие данные tenant или другого поставщика никогда не выдаются? |
| Идентификаторы | Стабильность внешнего ID, повторное использование SKU, различия источников одного поставщика, право платформы заменить mapping. |
| Синхронизация | Snapshot или delta; порядок, ревизия и время измерения; отсутствие позиции, деактивация и устаревание; статус частичного результата и reconciliation. |
| Повторы и конкуренция | Идемпотентность команды, срок receipt, конфликт одного ключа с другим payload, ожидаемая версия записи, восстановление потерянного ответа. Нынешние разные правила не объединены автоматически. |
| Объём и эксплуатация | Размер batch, пагинация, rate limits, ошибки и retry, наблюдаемость, аудит акторов, таймауты и отключение интеграции. |
| Совместимость | Версионирование конкретного контракта, уведомление о несовместимых изменениях и проверяемые примеры для клиента. `info.version` существующей HTTP-схемы не задаёт эту политику. |

Готовность к прототипу: выбран один сценарий, согласована матрица доступа и
владения, есть примеры успеха/ошибки/повтора/конфликта и способ выключить
интеграцию. Реализация credentials и новых маршрутов требует отдельной задачи;
эта документационная работа их не создаёт.
