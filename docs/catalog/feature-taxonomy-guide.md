# Feature Taxonomy Guide

## Назначение

Этот документ задаёт единый язык преимуществ климатической техники для менеджеров, импортёров и AI-агентов. Каждая `Feature` отвечает на один главный вопрос покупателя и имеет одну основную категорию.

Категория определяется не устройством функции внутри кондиционера, а пользой, которую первым делом получает покупатель.

Машиночитаемый источник истины: [`data/features/universal_v1.json`](../../data/features/universal_v1.json). Если документ и JSON расходятся, изменение нужно оформить одновременно в обоих местах.

## Категории

| Категория | Вопрос покупателя | Использовать для | Не использовать для |
|---|---|---|---|
| **Комфорт** | Насколько приятно пользоваться кондиционером каждый день? | мягкий поток, тишина, сон, автоматический комфорт | мощность, энергопотребление, Wi-Fi |
| **Воздух и очистка** | Что кондиционер делает с качеством воздуха? | приток, фильтрация, очистка, ионизация, контроль воздуха | медицинские обещания, способы управления |
| **Управление** | Как удобно управлять кондиционером? | приложение, Wi-Fi, голос, таймер, умный дом | экономия энергии, мощность |
| **Энергоэффективность** | Сколько будет стоить эксплуатация? | инвертор, ECO, снижение и контроль потребления | скорость охлаждения, зимний обогрев |
| **Производительность** | Справится ли кондиционер с моей задачей? | мощность, Turbo, скорость выхода на режим, большие помещения | зимний диапазон, шум |
| **Обогрев** | Можно ли использовать кондиционер зимой? | низкотемпературная работа, тепловой насос, +8 °C, зимний комплект | обычная холодопроизводительность |
| **Дизайн** | Как техника впишется в интерьер? | цвет, материал панели, дисплей, форма корпуса | рекламные слова без видимого отличия |
| **Надёжность** | Насколько долго и стабильно будет работать оборудование? | защиты, антикоррозийное покрытие, диагностика | шум, дизайн |
| **Монтаж и совместимость** | Подойдёт ли решение для моего объекта? | совместимость блоков, Free Match, трасса, особенности установки | технические параметры без покупательского смысла |

## Проверка перед созданием

1. **Аналог:** поискать существующий slug, название и aliases. Маркетинговое имя бренда не создаёт новую Feature, если покупательская польза та же.
2. **Feature или характеристика:** мощность `3,5 кВт` и шум `19 дБ` являются значениями. Feature нужна, если объясняет самостоятельный сценарий или пользу.
3. **Категория:** выбрать ровно один главный вопрос покупателя. Не раскладывать одну Feature одновременно по нескольким категориям.
4. **Польза:** краткое описание должно отвечать «что это даёт человеку», а не повторять название технологии.
5. **Область действия:** универсальную возможность не ограничивать брендом. Брендовой считается технология с уникальным смыслом, а не с уникальным названием.
6. **Источник:** для маркетинговых технологий сохранить официальный источник и точные ограничения применимости.
7. **Безопасность формулировок:** не превращать очистку воздуха в медицинское обещание, а защиту — в абсолютную гарантию.

## Scope и способ назначения

`scope` и назначение — разные понятия:

- `universal` означает, что смысл Feature одинаков для разных брендов;
- `brand` используется только для действительно фирменной технологии с отдельной пользой;
- `series` и `product` ограничивают применимость, но не обязаны создавать новую сущность Feature;
- `derived` в текущей модели означает автоматическое назначение по нормализованным характеристикам. Такая Feature всё равно может быть универсальной по смыслу.

Пример: «Встроенный Wi-Fi» универсален, назначается автоматически по `wifi_state=builtin`, а ссылка на конкретную серию определяет, где он реально присутствует.

## Спорные случаи

### Инвертор

- категория: **Энергоэффективность**;
- каноническая Feature: `inverter-control`;
- `Smart Inverter`, `DC Inverter` и похожие названия становятся aliases, если источник не доказывает отдельную покупательскую пользу.

### Wi-Fi

- категория: **Управление**;
- «Встроенный Wi-Fi» и `Wi-Fi Ready` — разные Feature, потому что во втором случае нужен отдельный модуль;
- названия фирменных приложений можно указывать в описании или override, не дублируя базовую Feature.

### Температура обогрева

- категория: **Обогрев**, не «Производительность»;
- общая Feature объясняет зимний сценарий;
- конкретное значение `−20 °C` выводится из характеристики модели и не должно плодить отдельные сущности для каждого порога.

### Уровень шума

- значение в децибелах остаётся характеристикой;
- «Низкий уровень шума» может назначаться как derived Feature по порогу, зависящему от типа блока;
- категория: **Комфорт**, не «Надёжность».

### Очистка воздуха

- `UVC`, ионизация и самоочистка имеют разные механизмы и не объединяются в одну Feature;
- фирменная многоступенчатая система вроде `QuadriPuri` может оставаться брендовой, если её состав и польза подтверждены;
- запрещены неподтверждённые обещания лечения, стерилизации комнаты и гарантированной защиты от вирусов.

## Автоматический аудит

Проверить библиотеку и canary-манифест:

```bash
python3 scripts/audit_feature_governance.py
```

Строгий режим для CI:

```bash
python3 scripts/audit_feature_governance.py --strict
```

Аудит проверяет:

- отсутствие или неизвестную категорию;
- совпадающие slug и aliases;
- расхождение с канонической категорией;
- универсальную Feature, ошибочно ограниченную брендом;
- брендовый термин, ошибочно объявленный универсальным;
- несколько активных Feature, соответствующих одному каноническому смыслу;
- подозрительно широкое назначение брендовой Feature всем сериям пилота.

## Будущий UX

Категории должны группировать преимущества на карточке товара и в подборе, а не быть техническим тегом:

```text
Комфорт
  Gentle Breeze
  Низкий уровень шума

Воздух и очистка
  FreshIN+
  УФ-обработка

Управление
  Встроенный Wi-Fi

Энергоэффективность
  Инверторное управление
```

Сначала показывается покупательский результат. Точное значение характеристики и источник раскрываются в деталях.
