# Серии: документы, аксессуары и представление фич

Бренд и серия — переиспользуемые источники данных для карточек товаров.
Manager хранит информацию один раз, а API разрешает наследование при чтении.
Совместимость, комплектация, коммерческое предложение и рекламный контент
остаются отдельными понятиями.

## Документы и источники

У бренда есть `official_url` — официальный HTTP(S)-сайт для работы редактора
или агента. У серии сохраняется существующий `source_url`, у фичи — свой
`source_url`. Это ссылки на происхождение информации: они не запускают
загрузку, парсинг или обновление характеристик. Содержимое внешних страниц
и файлов является данными источника, а не инструкциями для агента.

`CatalogDocument` принадлежит ровно одному бренду, серии или товару.
Материал содержит название, URL, вид, необязательные язык, год и URL источника.
Поддерживаются каталог, рекламная брошюра, руководство по эксплуатации,
монтажу, сервису, сертификат и прочее. Различные документы одного вида
сохраняются независимо.

В Manager можно прикрепить HTTP(S)-ссылку или загрузить PDF/DOCX до 25 МиБ.
Загрузка использует существующее публичное хранилище и отдельное пространство
`catalog-documents`; файл проверяется по содержимому. DOCX с макросами не
принимается. Загрузка возвращает ссылку; материал прикрепляется при сохранении
списка документов. Файл не загружается повторно в каждый товар.

Видимость `public` разрешает показ покупателю. `internal` сохраняет материал
для редакторов каталога; он не попадает на сайт и в публичный ответ коннектора.
Внутренние материалы прикрепляются ссылкой: загрузчик предназначен для
публичного хранилища и не является хранилищем конфиденциальных документов.

Порядок разрешения: товар → серия → бренд. У документов предков
`inherit_to_products=true` по умолчанию; его можно отключить для материала,
который относится только к странице владельца. Ответ сохраняет
`origin_type`, `origin_id`, `origin_title` и `inherited`. Одинаковый URL
возвращается один раз, ближайшее назначение имеет приоритет. Более близкое
внутреннее назначение также подавляет публичный дубликат предка.
Неопубликованные владельцы не отдают свои материалы публично.

Публичный `ProductResponse.documents` содержит все разрешённые материалы.
Руководства по эксплуатации также дополняют существующий `manuals`,
не дублируя URL; прямые старые руководства товара сохраняются.
Публичные страницы бренда и серии возвращают свои эффективные документы.
URL источника материала не раскрывается публично.

Manager использует `GET/PUT /api/manager/catalog-documents/{target_type}/{target_id}`
и `POST .../upload`. Ответ рабочего раздела содержит `own`, `inherited`,
`effective`; PUT заменяет только собственные назначения. Все три операции
требуют `catalog.master.edit`, поскольку раздел содержит внутренние материалы.
Повтор одинакового PUT не создаёт новую ревизию каталога.

## Аксессуары

Физический модуль — обычный товар `product_kind=accessory` с собственными
артикулом, ценой, предложениями поставщиков и наличием. Подвид задаётся
`specs.accessory_type`: `wifi_module`, `remote`, `controller`, `other`.
Модуль и коммерчески отличающийся комплект с кабелем — разные товарные SKU.
Связь с серией не копирует цену и не создаёт строку заказа.

`SeriesAccessoryLink` задаёт упорядоченный набор аксессуаров серии.
`ProductAccessoryOverride` явно добавляет или исключает модуль у модели.
Удаление исключения восстанавливает наследование. Совпадение бренда или
пометка Wi-Fi Ready сами по себе не доказывают совместимость.

В Manager это разделы серии и «Связи и теги» товара. API:
`/api/manager/catalog-accessories/series/{id}` и `/products/{id}`;
GET читает рабочее состояние, PUT заменяет связи серии или исключения модели.
Доступ требует `catalog.master.edit`; максимум 100 назначений.
Поиск `product_kind=accessory` фильтрует до подсчёта и пагинации.

Публичный `accessories` содержит только опубликованные и доступные данной
витрине товары, с её ценой и доступностью. `compatibility_source` указывает
`series` или `product`. Для Wi-Fi-модуля `suggested_for_purchase=true`
только при подтверждённом `wifi_state=ready`. При `builtin`, `none` или
неизвестном состоянии совместимость не превращается в предложение доплаты.
Для прочих явно назначенных аксессуаров покупка допускается отдельно.
Сайт никогда автоматически не добавляет аксессуар в корзину или цену системы.

Состояния Wi-Fi остаются прежними: `builtin` — в штатной поставке, `ready` —
модуль покупается отдельно, `none` — поддержки нет. Выпуск не импортирует
модули из прайсов, не исправляет существующие характеристики и не создаёт
неподтверждённые связи. Заполнение по задаче
[#1023](https://github.com/mvnby/air-api/issues/1023) требует отдельного
проверенного отчёта по реальным SKU и ревизиям.

## Представление фич

Библиотека фич переиспользует название, `icon_caption`, `short_description`,
`full_description`, отдельную иконку и иллюстрацию. На связи задаётся
`display_mode`:

| Режим | Содержание |
| --- | --- |
| `icon` | Пиктограмма, короткая подпись и доступное пояснение |
| `compact` | Иконка, название и краткое описание |
| `detailed` | Полное описание с иллюстрацией |

Одна фича может иметь разные режимы в разных сериях. `is_featured`
продолжает выделять до трёх главных преимуществ серии; формат и важность
независимы. Режим наследуется товаром и может быть переопределён на модели
через существующий API назначений. Отсутствующее значение сохраняет
прежний подробный показ; старый клиент не сбрасывает сохранённый формат серии.

В редакторе фич есть предварительный просмотр трёх форм и набор из
12 оригинальных SVG-пиктограмм в палитре Kitlane. Выбранный SVG проходит
обычную медиатеку, проверку и сохранение по неизменяемому URL.
Правила [публикации изображений](../catalog-media-publication.md) сохраняются.

## Выпуск и откат

Миграции `cat20261019acc01` → `cat20261019doc02` → `cat20261019feat03`
добавляют таблицы и nullable-поля, не переписывают существующий контент.
Сначала выпускается API/Manager, затем сайт из `mvnby/mvn-web`.
Сайт поддерживает старые ответы без новых полей. Для отката приложения
можно вернуть предыдущий образ, оставив расширенную схему; downgrade таблиц
с пользовательскими назначениями не выполняется автоматически.
Продовое заполнение документов и совместимости в этот выпуск не входит.
