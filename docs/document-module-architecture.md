# Модульная подсистема документов

## Решение

Документный контур развивается как изолированный модуль текущего приложения.
Он использует общую транзакционную PostgreSQL-базу, но не расширяет
`DocumentService`, `GoogleDocsService` и `OrderDocumentsPanel` новыми
обязанностями. Физическое выделение в самостоятельный network service возможно
только после стабилизации command/snapshot contracts и durable generation jobs.

Документный модуль владеет:

- юридическими лицами и профилями нумерации;
- внутренними и официальными реквизитами документа;
- версиями шаблонов;
- жизненным циклом `draft -> issued -> sent -> signed`;
- переходами `void` и `replaced`;
- снимком данных, использованным для выпуска;
- ссылками на неизменяемые артефакты и provider-owned editable copies.

CRM Core остаётся владельцем клиентов, заказов, предложений, строк, платежей и
договорных связей. Рендереры не читают ORM-граф CRM напрямую.

## Неизменяемый контекст генерации

Перед рендерингом application layer строит `DocumentContext`. Контекст содержит
только разрешённые и уже отфильтрованные значения:

- tenant и юридическое лицо;
- контрагента и выбранный филиал;
- заказ и выбранное предложение;
- продуктовые и сервисные строки;
- суммы и налоговый режим;
- документ-основание;
- подписантов и реквизиты.

Контекст не предоставляет шаблону произвольный доступ к базе и не изменяет
загруженные ORM-объекты. Один и тот же контекст должен воспроизводимо работать
с native DOCX и Google adapters.

## Номера и выпуск

`internal_reference` остаётся стабильным CRM-идентификатором. Юридические поля
`official_series`, `official_number`, `official_period_key` и `official_date`
хранятся отдельно.

Официальный номер резервируется атомарно в области:

```text
tenant + legal entity + document kind + series + period
```

Резервирование никогда не переиспользуется. Ошибка рендера после резервирования
сохраняет диагностируемое состояние, а не возвращает номер в последовательность.
Выпущенный документ не перезаписывается: исправление создаёт замену, а исходный
документ переводится в `void` или `replaced` по явной команде.

## Шаблоны

Шаблон имеет provider-neutral identity и неизменяемые версии. Новая редакция не
меняет ранее выпущенные документы. При загрузке версия проходит проверку DOCX,
каталога плейсхолдеров и табличных якорей; только после этого её можно явно
активировать.

Поддерживаемые адаптеры:

- `native_docx` — основной путь без внешнего аккаунта, включая бумажные
  ТН-2/ТТН-1 по загруженному шаблону;
- `google_docs` — опциональная редактируемая копия или Google template;
- `google_sheets` — совместимость текущих бумажных ТН/ТТН во время перехода.

Нативный DOCX преобразуется в PDF внутренним Gotenberg/LibreOffice adapter.
Сервис не публикует порт наружу и не получает доступа к CRM или базе данных.

Google file id и edit URL являются provider mapping, но не источником истины.
Выпущенный PDF/DOCX и metadata snapshot сохраняются отдельно.

## Заполненность клиента в выбранном нативном действии

Для `contract`/`invoice`/`act` application service проверяет effective placeholders
реальных DOCX bytes после применения frozen conditions через существующий
`DocxConditionProcessor`. Отключённые first/even Word headers/footers не
добавляют требований; активные inherited stories учитываются. Общий security
каталог загрузки/рендера остаётся прежним. Проверка использует raw factual snapshot; линии для
заполнения принадлежат только выходному документу. Требования не выводятся из
общей сводки карточки. Политика полей и UI описаны в
[рабочей области клиента](customer-workspace.md#проверка-клиента-для-выбранного-договора-счёта-или-акта).

`POST /api/manager/document-system/orders/{order_id}/documents/readiness`
принимает draft selection и возвращает `checked`, `missing_fields` (field,
label, critical), `can_issue`, template/version IDs. Это read-only preflight:
создание повторяет факты и актуальный выбор, и по умолчанию отклоняет критичные
пропуски. `allow_incomplete_customer=true` явно разрешает неполный черновик.
`GET /api/manager/document-system/documents/{document_id}/readiness` читает
scoped saved draft без provider calls и без обновления снимка. Manager использует
его перед синхронизацией внешнего редактора для выпуска. Сам `issue` повторяет
проверку actual saved template/version/source/facts до резервирования номера и
артефактов; отсутствие, повреждение или устаревание cached readiness не дают
разрешения на выпуск. Уже issued/sent/signed записи не пересчитываются.

Пометка неполного черновика добавляется к output copy в body и каждый активный
вариант header всех sections, включая first/even page; исходный tenant template
не изменяется. Редактируемый DOCX сохраняет пометку; preview повторно добавляет
её и к синхронизированному source, если пользователь удалил её в редакторе.
Скачивание draft DOCX проходит через private API presentation guard; presigned
URL к storage для такой копии не выдаётся. Этот guard меняет только response
bytes, проверяя сохранённые факты/шаблон, и не переписывает stored artifact.
Issued artifacts сохраняют существующий путь доступа и исходные bytes.
Изменение карточки не обновляет сохранённые факты, существующие номера или файлы.

## Хранилище и приватность

Документные артефакты приватны и tenant-scoped. Публичные URL и общий media
bucket не используются. Доступ к скачиванию проходит через авторизованный API
или короткоживущую signed URL. Storage adapter не принимает tenant id из
непроверенного клиентского payload.

## Совместимость

Переход выполняется additive expand-моделью:

- существующие `OrderDocument` и `DocumentTemplate` продолжают читаться;
- legacy Google-документы не перегенерируются и не переносятся автоматически;
- новые поля scope/lifecycle могут оставаться пустыми только у legacy rows;
- текущие API сохраняются до переключения Manager UI;
- backfill исторических документов требует отдельного read-only плана и явного
  выполнения после проверки provider files.

## Граница физического выделения

Первым отдельно масштабируется stateless renderer/worker: он принимает шаблон и
`DocumentContext`, возвращает артефакт и не имеет доступа к CRM-таблицам.

Весь документный модуль может стать самостоятельным сервисом только когда:

- generation jobs переживают restart и имеют lease/idempotency contract;
- CRM передаёт versioned snapshot, а не разрешает читать свои таблицы;
- numbering/lifecycle API стабилен;
- provider calls не находятся внутри бизнес-транзакции;
- extraction не требует shared-database writes.

## Вне текущего эпика

- ЭСЧФ;
- юридически значимые электронные ТН/ТТН и EDI/ЭЦП;
- автоматический перенос или перегенерация исторических документов;
- физическое выделение документной базы или network service.

## Дефектный акт по замечаниям ТО

`MaintenanceActPreparationService` владеет явной командой продолжения ТО и
подготовки native `maintenance_defect_act`. `MaintenanceActSource` сохраняет
ссылки на неизменяемые ревизии наблюдений; специализированный snapshot builder
добавляет отдельные factual/recommendation blocks и приватные source references.
`DocumentContextBuilder` передаёт этот сценарий отдельному builder, а
`ManagedDocumentService` сохраняет черновик в транзакции команды и далее
использует штатные preview/issue/replacement/delivery. Фасад `DocumentService`
не получает новых обязанностей. Общее создание документа без явного выбора
замечаний не допускается. Хранение, конкурентность и rollout описаны в
[правилах ТО](equipment-maintenance.md#явная-подготовка-дефектного-акта-1085-второй-срез).


Коммерческое продолжение ТО находится в `MaintenanceOfferService`: immutable
снимки штатных предложений, отдельные события выпуска/отправки/ответа клиента
и явное продолжение той же ремонтной карточки. Эти события не заменяют lifecycle
native дефектного акта и не вызывают `DocumentService`; акт допустим до согласия.
Согласованный состав и фактическое устранение связаны отдельными источниками,
см. [коммерческий процесс ТО](equipment-maintenance.md#решение-хранения-коммерческого-продолжения-1085).
