# Git workflow

Один PR — одна логическая задача. `main` обновляется только через PR с зелёным
CI; текущая задача включает коммит, push, PR и squash merge после проверок,
если пользователь явно не ограничил её анализом или подготовкой без публикации.

## Ветка и рабочее дерево

Сначала проверьте текущую ветку и `git status --short`. Сохраните чужие и
несвязанные изменения: не включайте их в коммит, не откатывайте и не прячьте
автоматически. Продолжайте подходящую ветку текущей задачи; для новой работы
используйте актуальный `origin/main`. При конфликтующей параллельной работе
нужен отдельный checkout/worktree.

Пример для новой задачи, когда рабочее дерево позволяет безопасно сменить ветку:

```bash
git fetch origin
git switch -c korotov/short-task-name origin/main
```

По умолчанию используйте `korotov/` и короткое имя по смыслу задачи; явно
заданное пользователем имя имеет приоритет. Срочный фикс проходит тот же
процесс, с минимальным объёмом изменений и пометкой `hotfix` в PR.

## Изменения и локальная проверка

Выберите проверки из
[verification by change](development-workflow.md#verification-by-change).
Там находятся команды тестов и генерации API-клиента. Локальные проверки
выбираются по изменению; обязательная CI-матрица сохраняется.

Для API-изменений можно один раз подключить существующий hook:

```bash
./scripts/setup_git_hooks.sh
```

Он синхронизирует и добавляет в индекс OpenAPI/Manager client при изменении
отслеживаемых API-файлов. Hook не заменяет проверку diff и сборку Manager.

Перед коммитом просмотрите diff и добавьте только файлы текущей задачи:

```bash
git add -- path/to/changed-file.md
git diff --cached --check
git diff --cached --stat
git diff --cached
git commit -m "Docs: clarify agent workflow"
```

Пути и сообщение выше — пример. После hook убедитесь, что добавленные generated
файлы относятся к задаче. В коммите не должно быть временных артефактов, секретов
или случайных изменений.

## PR и merge

1. Запушить рабочую ветку: `git push -u origin HEAD`.
2. Открыть PR в `main` по [шаблону](../.github/pull_request_template.md): проблема
   и результат, фактически выполненные проверки, существенные риски и выпуск.
3. Проверить CI именно для текущей ревизии PR. После нового коммита старый
   зелёный результат недостаточен; отсутствие checks не означает успех.
4. Дождаться всех обязательных проверок и устранить замечания, блокирующие merge.
   Не пропускать тесты или release gates ради скорости.
5. Выполнить squash merge. Не пушить рабочие изменения напрямую в `main`.

Во время CI используйте ограниченный по времени watcher конкретного PR/run,
например `gh run watch <run-id> --exit-status` с лимитом ожидания в среде агента.
Если checks ещё не привязались к PR, найдите run по ветке и commit. Читайте
подробные логи при сбое; не запрашивайте неизменившиеся статусы частым циклом
через модель. Пользователю сообщайте изменение статуса, причину задержки или итог.

## После merge

Проверьте CI для merge-коммита и статус вызванного им deployment.
Текущий [deploy workflow](../.github/workflows/deploy.yml) запускается после
успешного CI на `main`, в том числе для изменения документации. Если в будущем
триггеры изменятся, сверяйте фактический run, а не предполагайте выпуск.

Для запущенного deployment выполните итоговую проверку по
[процедуре деплоя](deployment.md): `/api/health`,
`/api/v1/products?limit=5`, `/api/v1/filters/config` должны пройти smoke-check.
Следуйте применимой HA-процедуре; сам merge не доказывает успех выпуска.

## Рискованные изменения

Миграции и post-deploy шаги должны иметь порядок выполнения, критерий успеха
и план отката в PR или связанном runbook. Продовые операции с данными подчиняются
[production data operations](production-data-operations.md): пример команды
в PR не заменяет необходимые разрешения и reviewed plan.

Не смешивайте несвязанный рефакторинг с feature/fix. В итоговом отчёте отделяйте
локальные проверки, CI, merge и runtime verification; указывайте оставшийся
блокер, если какой-либо обязательный этап не завершён.
